# BLOG_RUNTIME_CANON.md

**Проект:** MyWave Site + Parser_News  
**Статус документа:** Канон для текущего контура + целевое состояние до полной рабочей версии  
**Версия:** v1.0  
**Дата:** 2026-03-27

---

## 1. Назначение документа

Этот документ фиксирует:

1. **что считать подтверждённым рабочим контуром блога сейчас**;
2. **что считать legacy / неподтверждённым**;
3. **какое целевое состояние считается обязательным**, чтобы можно было утверждать, что:
   - локальный проект и GitHub совпадают;
   - блог работает автоматически;
   - сайт показывает новости в оформленном виде;
   - есть понятная админка для редактирования текста, обложки и медиа;
   - видео из источника отображается на сайте онлайн, без обязательного полного скачивания в хранилище сайта.

Документ разделяет:

- **Current Canon** — подтверждённая рабочая схема;
- **Target Canon** — обязательное целевое состояние;
- **Definition of Done** — условия, при которых раздел «Блог» считается доведённым до полного рабочего уровня.

## 2. Термины

### 2.1 Parser_News
Система сбора, нормализации, review-подготовки и записи новостей в Google Sheets.

### 2.2 Site_MyWave
Сайт, который читает данные блога, рендерит `/blog`, `/blog/<slug>`, блок последней новости на главной, и предоставляет админский интерфейс.

### 2.3 `raw_feed`
Канонический внешний обменный слой между Parser_News и сайтом.

### 2.4 Canonical Source of Truth
Единственный источник, по которому определяется, должен ли материал отображаться на витрине и в каком виде.

### 2.5 Legacy path
Любой альтернативный контур, который не подтверждён текущим рабочим кодом и/или прод-деплоем.

---

## 3. Current Canon (подтверждённое текущее состояние)

### 3.1 Канонический контур публикации на текущий момент

До формального пересмотра архитектуры **каноническим рабочим контуром** считается:

```text
Parser_News -> Google Sheets(raw_feed) -> Site_MyWave читает raw_feed -> /blog, /blog/<slug>, /api/blog/*
```

### 3.2 Канонический источник истины

**Source of Truth для внешнего обмена и витрины:** `raw_feed`.

Сайт может использовать локальную БД как fallback / sync-слой / read-резерв, но **не как самостоятельную конкурирующую правду**, если она расходится с `raw_feed`.

### 3.3 Канонические правила publishability

Материал считается допустимым для показа на витрине, если одновременно:

1. `status` после нормализации входит в `{READY_TO_PUBLISH, PUBLISHED}`;
2. `status != ARCHIVED`;
3. есть publishable content (непустое хотя бы одно из полей контента).

### 3.4 Что не входит в publishability v1

Следующие поля **не должны** сами по себе определять показ на витрине:

- `published_posts`
- `final_ready`
- `telegram_published`
- `APPROVED` как самостоятельный статус

### 3.5 Текущая модель чтения сайта

Подтверждённая рабочая модель сайта:

- `/blog` и `/blog/<slug>` читают данные через blog-store;
- источник чтения: **Sheets primary**, **DB fallback**;
- XLSX-файлы не являются runtime-источником витрины;
- legacy path через `news_articles` не должен считаться каноном без отдельного подтверждения.

---

## 4. Что считать legacy / неподтверждённым

До отдельного подтверждения кодом и деплоем **не считать production-каноном**:

- `news_articles` как альтернативный равноправный источник витрины;
- Apps Script `onEdit` как обязательный publish-механизм;
- `/api/news/publish` как активный production route;
- любые ручные или локальные сценарии, которые не зафиксированы в текущем repo и не подтверждены на сервере.

Если какой-либо из этих путей реально существует на проде, он должен быть:

1. найден в коде;
2. задокументирован;
3. покрыт проверками;
4. либо переведён в канон, либо помечен как legacy и выведен из эксплуатации.

## 5. Product Decision: целевое состояние, обязательное к достижению

Ниже — не просто описание желаемого результата, а **обязательные продуктовые решения**, которые должны стать реальностью.

### 5.1 GitHub и локальная версия — один и тот же проект

Система считается корректной только если:

1. локальный проект и GitHub-репозиторий совпадают по структуре и логике;
2. есть **одна главная ветка**, которая считается полной рабочей версией;
3. локальные незапушенные изменения не могут считаться «реальным состоянием проекта» дольше согласованного короткого окна разработки;
4. прод-деплой должен быть привязан к конкретному commit / tag;
5. можно однозначно ответить на вопрос: **какой commit сейчас у локальной версии, какой в GitHub, какой на сервере**.

#### Обязательная политика синхронизации

- GitHub = главный удалённый канонический репозиторий;
- локальная рабочая копия = синхронизированная производная GitHub;
- прод = деплой конкретного commit из GitHub;
- любые изменения в Parser_News и Site_MyWave, влияющие на блог-контур, должны проходить через commit с понятным сообщением и сверкой контрактов.

#### Запрещённое состояние

Нельзя считать проект доведённым до рабочего уровня, если:

- локально работает одно, а в GitHub лежит другое;
- в GitHub одно, а на сервере крутится другая версия;
- прод-контур определяется «по памяти» или по переписке, а не по зафиксированному коду.

---

### 5.2 Блог должен работать автоматически

Под «работает автоматически» в этом документе понимается:

1. Parser_News записывает и обновляет данные в `raw_feed` по контракту;
2. сайт автоматически читает новые и обновлённые записи из канонического источника;
3. посты, удовлетворяющие publish-условиям, появляются на витрине без ручного копирования текста в шаблоны;
4. есть прогнозируемый sync/update-path;
5. есть диагностика ошибок и застрявших записей.

#### Обязательные свойства автоматизации

- один канонический publish-path;
- одна status-модель;
- одна схема ownership полей;
- одна read-model для витрины;
- наблюдаемость: логи, smoke-check, понятный health-check для блога.

---

### 5.3 На сайте должен быть полноценный оформленный блог

Обязательное целевое состояние сайта:

#### Витрина
- `/blog` — список постов;
- `/blog/<slug>` — детальная страница поста;
- на главной — блок последней новости / последних новостей, подключённый к реальному источнику, а не статическая заглушка;
- корректная пагинация;
- фильтр по тегам;
- поиск по блогу;
- корректное SEO для листинга и поста.

#### Контент
- заголовок;
- краткое описание / excerpt;
- основной текст;
- обложка;
- теги;
- дата публикации;
- источник / ссылка на источник при наличии;
- безопасный HTML-рендер;
- корректная обработка markdown / HTML / plain text.

#### SEO и discoverability
- canonical для `/blog` и `/blog/<slug>`;
- meta title / description;
- OpenGraph для постов и листинга;
- валидный slug;
- отсутствие дублей и legacy-маршрутов, создающих SEO-шум.

---

### 5.4 Админка блога должна быть понятной и рабочей

Целевое состояние требует **полноценной blog-admin UI**, а не только управление через Google Sheets.

#### Минимально обязательные функции админки

1. список постов;
2. просмотр карточки поста;
3. редактирование:
   - заголовка;
   - excerpt;
   - основного текста;
   - slug;
   - тегов;
   - обложки;
   - SEO-полей;
   - статуса публикации;
4. предпросмотр поста до публикации;
5. публикация / снятие с публикации;
6. архивирование;
7. отображение источника и статуса синхронизации;
8. отображение того, какие поля пришли из Parser, а какие были изменены на стороне сайта;
9. история последнего обновления;
10. безопасная авторизация и разграничение доступа.

#### Обязательная модель работы админки

Админка должна работать **поверх канонического контракта**, а не создавать второй независимый контур данных.

Это означает:

- либо админка пишет обратно в `raw_feed` только разрешённые site-owned поля;
- либо админка работает через отдельную каноническую БД-модель, но тогда это должна быть официальная миграция архитектуры и отказ от прямого конкурирующего чтения из Sheets.

Гибрид без правил ownership запрещён.

---

### 5.5 Обработка обложки и медиа обязательна

#### Обложка
Каждый publishable пост должен поддерживать:

- `cover_image_url` как каноническое поле витрины;
- fallback из legacy-полей (`image_url`, `raw_media`) только на этапе нормализации;
- ручную замену обложки через админку;
- валидацию URL / формата;
- отображение на листинге, на странице поста и в OpenGraph.

#### Галерея / дополнительные изображения
Рекомендуется поддержать отдельное поле списка медиа (`media_items` / JSON), но это не обязательное условие v1, если есть хотя бы корректная обложка.

---

### 5.6 Видео должно отображаться онлайн, без обязательного полного скачивания

Это обязательное целевое требование.

#### Каноническое решение для видео

Если у источника есть видео, сайт должен поддерживать **embed / streaming-first подход**:

1. сайт **по умолчанию не скачивает видео полностью** в своё хранилище;
2. сайт хранит ссылку, embed URL или ссылку на внешний player;
3. на странице поста видео показывается через безопасное встраивание;
4. если прямое встраивание невозможно, сайт показывает превью + ссылку на просмотр;
5. локальное скачивание видео допускается только как отдельный осознанный режим, а не как обязательный путь по умолчанию.

#### Канонические поля для видео (target extension)

В канонический read model должны быть добавлены поля:

- `video_url` — исходная ссылка на видео;
- `video_embed_url` — нормализованная ссылка для безопасного встраивания;
- `video_platform` — youtube / vk / rutube / telegram / drive / other;
- `video_preview_image_url` — превью видео;
- `video_duration` — опционально;
- `has_video` — булево поле для витрины.

#### Правила отображения видео

- при наличии валидного `video_embed_url` пост показывает встроенный плеер;
- при отсутствии embed, но наличии `video_url` — показывается безопасная ссылка / кнопка просмотра;
- видео не должно ломать layout карточки и поста;
- CSP и allowlist доменов должны поддерживать разрешённые видеоплатформы.

## 7. Ownership полей

### 7.1 Parser-owned
Parser_News отвечает за ingest и первичное наполнение контентных полей, если иное не переопределено редакторским режимом.

### 7.2 Site-owned
Сайт отвечает минимум за:

- `slug` (если сайт нормализует его сам)
- `canonical_url`
- `seo_title`
- `seo_description`
- editorial-правки витринных полей, если они разрешены продуктом
- embed-нормализацию видео
- поля публикации и отображения, если это определено контрактом

### 7.3 Жёсткое правило

Ни Parser_News, ни сайт не должны бесконтрольно перетирать поля другого владельца.

Все ownership-правила должны быть зафиксированы в одном контракте и соблюдаться одинаково:

- в sync;
- в publish pipeline;
- в админке;
- в импортах;
- в ручных операциях.

## 8. Канонический runtime flow

```text
[Источник новости]
    -> Parser_News ingest
    -> normalize / dedupe / enrich
    -> write to raw_feed
    -> status review/publish gating
    -> Site_MyWave read from raw_feed
    -> normalize to canonical post model
    -> render /blog and /blog/<slug>
    -> optional sync to DB fallback/cache
    -> expose latest post on homepage
```

### 8.1 Единственно допустимые варианты на runtime

#### Допустимо
- `raw_feed -> Site read model -> render`
- `raw_feed -> sync -> DB fallback -> render`

#### Недопустимо без отдельного решения
- `raw_feed` и `news_articles` одновременно как равноправные источники витрины;
- ручное копирование постов в шаблоны сайта;
- отдельная админка, которая пишет в свою модель без синхронизации и ownership-правил;
- два разных критерия publishability в разных слоях.

## 11. Definition of Done

Можно говорить, что «Блог выполнен на 100%», только если одновременно выполнены все условия:

1. **Git parity**
   - локально, на GitHub и на сервере один и тот же кодовый контур.

2. **Runtime canon**
   - production использует один канонический publish path;
   - нет скрытых альтернативных прод-путей.

3. **Automatic blog pipeline**
   - новые publishable записи автоматически попадают на сайт.

4. **Working homepage integration**
   - главная выводит последнюю новость из реального источника.

5. **Working editor/admin**
   - редактор может через UI менять текст, обложку, теги, slug, статус, SEO и медиа.

6. **Video-ready content model**
   - видео из источника отображается онлайн безопасным способом.

7. **Observability**
   - есть smoke-check, health-check и понятные логи.

8. **Documentation**
   - этот документ и связанные контракты соответствуют реальному коду.

Если хотя бы один пункт не выполнен, формулировка «выполнено на 100%» не допускается.

До отдельного архитектурного пересмотра:

- **канонический внешний обменный слой** — `raw_feed`;
- **канонический runtime path сайта** — чтение сайта из `raw_feed` с допустимым DB fallback;
- **канонический курс развития** — один кодовый контур между локальной версией, GitHub и продом;
- **обязательное целевое развитие** — полноценная автоматическая витрина + понятная админка + онлайн-отображение видео.

Любое отклонение от этого должно оформляться как новая версия канона, а не как неявная локальная логика.
