# Блог/Новости: backlog доведения до целевого уровня (blog-only)

## 1) Что обнаружено

- Базовый модуль блога рабочий, но есть разрывы относительно целевого состояния: нет latest news на главной, нет поиска, нет активных категорий, SEO листинга неполный, есть legacy-шаблон с неактуальным контрактом.

## 2) Почему это важно

- Эти разрывы влияют на UX, SEO и управляемость контента.
- Закрыть их можно малыми совместимыми шагами без массового рефакторинга.

## 3) Предлагаемое решение

- Выполнить 5 последовательных шагов с независимыми rollback points.
- Сохранить текущую схему данных и контент-поток из Sheets как baseline.

## 4) Какие файлы затрагиваются

- `app/routes/blog.py`
- `app/services/blog/store.py` (точечно, если добавим поиск/фильтры на уровне store)
- `templates/blog/index.html`
- `templates/blog/post.html` (минимально, только если унификация SEO)
- `templates/index.html`
- `static/js/*` (только при выборе client-side рендера latest-post)
- `templates/base.html` (только если нужно централизовать canonical-политику)
- `tests/unit/*`, `tests/integration/*` (новые/обновленные тесты блога и главной)

## 5) Что переносим как есть

- Роуты `/blog`, `/blog/<slug>`, `/api/blog/latest`, `/api/blog/posts`.
- Поток данных Sheets -> fallback DB.
- Markdown/sanitize рендер и текущие publish статусы.

## 6) Что рефакторим

### Шаг 1. Подключить последний пост на главной

- Изменение:
  - либо server-side подача latest post в `home()` (`app/__init__.py`),
  - либо client-side через `/api/blog/latest`.
- Предпочтительно: server-side (меньше JS-зависимости, SEO-дружественнее).
- DoD:
  - в секции `#blog` на главной показывается реальный последний пост;
  - при отсутствии постов показывается аккуратный fallback-текст.
- Rollback:
  - откат только правок главной (`app/__init__.py`, `templates/index.html`).

### Шаг 2. Добавить поиск по блогу

- Изменение:
  - query `?q=...` в `/blog`, фильтр по `title/excerpt/content_md`.
  - форма поиска в `templates/blog/index.html`.
- Важно:
  - сначала фильтрация, затем пагинация (не наоборот).
- DoD:
  - поиск работает совместно с тегами и пагинацией;
  - пустой поиск не ломает текущий листинг.
- Rollback:
  - откат изменений в `app/routes/blog.py` и `templates/blog/index.html`.

### Шаг 3. Принять решение по категориям (один вариант)

- Вариант A (быстрый): удалить legacy UI-следы категорий, оставить теги как единственную таксономию.
- Вариант B: ввести реальные категории в контракт данных и UI.
- Рекомендация на текущем этапе: Вариант A, чтобы убрать ложный интерфейс и не расширять схему без необходимости.
- DoD:
  - в коде и шаблонах нет "мертвых" ссылок на старый category flow.
- Rollback:
  - откат удаления/правок legacy-шаблона.

### Шаг 4. Унифицировать SEO для `/blog` и `/blog/<slug>`

- Изменение:
  - добавить canonical для листинга `/blog`;
  - при необходимости явно задать OG для листинга.
- DoD:
  - predictable SEO-контракт: title/description/canonical/OG на обеих страницах.
- Rollback:
  - откат только шаблонных правок SEO-блоков.

### Шаг 5. Зафиксировать контент-контракт полей

- Изменение:
  - документировать canonical mapping полей:
    - `cover_image` -> `cover_image_url`
    - `tags` -> `tags_json` + computed list
    - `author` -> решение (добавляем поле позже или используем `source_name`)
  - при необходимости добавить `author` в модель/поток отдельным мини-этапом.
- DoD:
  - единый договор по полям для backend/template/import.
- Rollback:
  - документация и небольшие backward-compatible маппинги.

## 7) Что откладываем

- Полноценный UI-редактор блога в админке (workflow, approve, версионирование).
- Глубокая интеграция блога в доменные карточки `events/services/projects`.
- Полнотекстовый индекс (если не подтверждена нагрузка и потребность).

## 8) Риски

- Фильтрация+пагинация может поменять видимость постов для пользователей (ожидаемый, но контролируемый эффект).
- Добавление поиска в лоб по in-memory данным может быть затратным при большом объеме (нужно ограничить scope/пагинацию).
- Разные пути формирования canonical (HTML vs writeback в Sheets) могут разъехаться без единого правила.

## 9) Критерий готовности

- На главной реально отображается последний пост.
- На `/blog` работают теги, поиск, корректная пагинация.
- Нет активных legacy-артефактов, вводящих в заблуждение.
- SEO-контракт для list/post унифицирован и проверен.
- Все изменения ограничены разделом `Блог/Новости`, без побочных рефакторингов.

## Последовательность и зависимости

1. Шаг 1 (latest post on home) — независим.
2. Шаг 2 (search) — зависит только от текущего `/blog`.
3. Шаг 3 (categories decision) — после шага 2, чтобы не мешать UX-тесту.
4. Шаг 4 (SEO unify) — после стабилизации шаблонов.
5. Шаг 5 (field contract) — финализация документации/контракта.

Rollback point после каждого шага — отдельный commit/PR с изолированными изменениями.
